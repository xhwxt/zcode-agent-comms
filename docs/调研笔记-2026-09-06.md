# 任务看板前期调研（2026-09-06）

> 结论先行：ZCode 侧"看板数据"基本不用自己造——客户端任务索引、会话库 `todo` 表、token 用量表三层现成；跨 agent 共写层有已审计的 `zcode-agent-board`（文件+原子锁）可参考；GitHub 上最强同类 `vibe-kanban`(28k★) 官宣 sunsetting，品类有需求但"大而全"难跑通，自研小而美定位合理。

## 一、项目目标

自研任务看板。第一阶段支持 ZCode；后期扩充到 Codex、Hermes Agent 等其它 coding agent。

## 二、本地数据面（ZCode 侧可用数据源）

### 1. 客户端任务索引 `~/.zcode/v2/tasks-index.sqlite`（ZCode 桌面端"任务"列表的数据源）
- `tasks` 表（98 行）：`task_id` 就是会话 id（sess_ 前缀）、`title`、`task_status`（实测只有 completed/error/null，**运行中任务不落此库**）、`provider/model/mode`、`workspace_path`、pinned/archived/deleted、`searchable_text`。
- `task_groups` / `task_group_members`：客户端任务分组功能（当前只有 cron / off-peak 两个内置组）。
- `automations`（定时任务）、`automation_runs`、`off_peak_tasks`（闲时队列）。

### 2. 会话深数据 `~/.zcode/cli/db/db.sqlite`（约 777MB，WAL 模式，zcodetoken 已在只读使用）
- `session`：id、`parent_id`（子代理归属）、directory、title、task_type、`summary_additions/deletions`（代码变更统计）、时间戳组。
- `todo`：TodoWrite 落库（session_id / content / status: pending|in_progress|completed / priority / position）——**天然就是看板三列**。
- `message` / `part`：完整对话与工具明细；part 里含 Agent 派发的 `description`（子代理任务名，zcodetoken v52 已踩坑：任务名必须用回执 `agentId:` 硬关联，勿用时间配对）。
- `model_usage` / `turn_usage` / `tool_usage`：每请求 token/耗时/工具/错误——看板可显示进度与成本。
- `session_target`：目标驱动模式（objective、token_budget、tokens_used、status）。
- `workflow_*` / `session_task_link`：0 行，官方预留的工作流脚手架，当前未启用（升级时注意会不会启用）。

### 3. zcodetoken（自有项目）已验证的机制
- MCP 注册：`~/.zcode/cli/config.json` 的 `mcp.servers` —— 对话内读写看板的现成通道。
- **UI 路线**：官方插件机制（plugin.json）只有 MCP/skills/commands/hooks，没有 UI 能力；要画进 ZCode 主窗口只能 asar 注入 overlay（ZCode 升级会覆盖，需重跑 install）。
- 事件驱动：fs.watch 监视 db 三件套 mtime（WAL 主要落 -wal）+ 常驻 python 泵；会话跟随走客户端 IPC `zcode:sync-active-task-session`。
- 启发：若做**独立 Web 看板**则完全零注入——只读 db + 文件即可，不受 ZCode 升级影响。

### 4. 已审计的看板先例：`zcode-agent-board`
位置：`~/.zcode/workspace/default/_audit_zcode-agent-board/`（源：github.com/zheyu-Julie-Liu/zcode-agent-board，1★，2026-09 活跃）。
- 形态：纯文件 + POSIX 原子锁，项目根 `.agent-board/`：`tasks/*.json`（临时文件+rename 原子写）、`locks/*.lock`（O_CREAT|O_EXCL 抢锁）、`events.jsonl` 流水、`config.json`。
- 语义：`claim` 原子认领（两 agent 绝不抢同一单）/ `done` 交单 / `comment` 交接（同时续约锁）/ `feed` 流水 / `touch` 续约 / `steal` 接管（锁 30 分钟无活动）/ `add --parent` 拆子任务 / `boss` 身份最高优先级。
- 落地形式：skill（对话中自动触发）+ `/board` 命令 + MCP 12 个 `board_*` 工具 + AGENTS-snippet 注入"空闲必看板"铁律。
- **完全 agent 无关**（任何支持 skill/MCP/Bash 的 agent 都能读写）——正是"先 ZCode 后 Codex/Hermes"想要的协议层参考。

### 5. 桥接先例（`~/.zcode/workspace/default/_audit_bridges/`）
- `coder-mcp-bridge`：把 ZCode/OpenCode/Pi 映射为统一 `agent-*` MCP 工具的调度桥（多 agent 统一控制面的现成参考）。
- `zcode-open-bridge`（tizerluo）：把 ZCode 接入 MCP/ACP 开放生态。

## 四、关键洞察

1. **数据不用自己造**：ZCode 侧三层现成数据——tasks-index（任务列表）+ db.sqlite `todo`/`session`（进度与详情，todo 表直接映射看板三列）+ usage 表（成本）。跨 agent 共写层用 `.agent-board` 式文件协议。
2. **UI 路线建议先独立 Web**：本地起服务只读 db + 看板文件，零注入、零升级破坏（claude-task-viewer / vibe-kanban 同款形态）；"嵌入 ZCode 窗口"的 asar 注入路线 zcodetoken 已证明可行但维护成本真实（每次升级重装），可作后期增强。
3. **跨 agent 的正确抽象是适配器 + 文件协议**：zcode-agent-board 证明文件+锁天然 agent 无关；coder-mcp-bridge 证明 MCP 统一 `agent-*` 接口可行。ZCode 深度集成（读原生 todo/usage），Codex/Hermes 只需实现同一套看板文件协议即可接入。
4. **品类信号**：vibe-kanban sunsetting 说明"大而全商业看板"难跑通，但需求真实；自研面向自己的小而美合理。
