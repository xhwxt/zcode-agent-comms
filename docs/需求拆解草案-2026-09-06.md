# 任务看板需求拆解草案 v0.1（2026-09-06，讨论稿）

> 定位一句话：**你在 Web 看板上发任务，看板调 AI 理解并拆解成任务卡，ZCode 自主接单执行，你只验收结果。** 后期把执行端扩到 Codex、Hermes。

## 1. 核心循环

```
你发任务（自然语言 + 可选附件/工作区路径）
   ↓
【拆解】无人值守 ZCode 会话理解任务 → 产出任务卡：说明 / 验收标准 / 依赖 / 优先级
   ↓
【放行】你过目拆解结果，一键放行（或按任务开"自动放行"）
   ↓
【接单】看板调度器按优先级/并发上限派给执行 agent（外部对话未来也可走协议抢单）
   ↓
【执行】一任务 = 一个 ZCode headless 会话；进度/成本从共享数据库实时读出上板
   ↓
【回报】完成 → 结果摘要 + 变更清单 → 进入"待验收"
   ↓
【验收】你看摘要/diff → 通过（完成）｜打回（留言回流，agent 续做或重开）
```

看板列（状态机）：`收件箱 → 拆解中 → 待放行 → 待接单 → 执行中 → 待验收 → 完成`，外加 `失败/冻结`。

## 2. 角色

| 角色 | 是什么 | 说明 |
|---|---|---|
| 老板（人） | 你 | 发任务、放行、验收、打回；意见最高优先级 |
| 拆解员 | 无人值守 ZCode 会话 | 每张原始任务跑一次，产出结构化任务卡（JSON 校验不合格自动重试） |
| 执行 agent | ZCode headless 会话 | 一任务一会话；后期 Codex/Hermes 做同构适配器 |
| 看板服务 | 本机 Web 服务 | 任务状态机 + 调度 + UI；本身不"智能"，智能全部通过调 agent 获得 |

## 3. 模块清单

| 模块 | 内容 | 阶段 |
|---|---|---|
| M0 数据与协议 | 任务卡 schema、状态机定义、文件+原子锁协议（跨 agent 通用）、SQLite 存储 | MVP |
| M1 Web 看板 UI | 列视图、任务卡、详情页（说明/验收标准/执行日志/成本/变更文件）、发任务表单、拖拽改列 | MVP |
| M2 看板 API | 任务 CRUD、状态流转、锁、调度器（优先级+并发上限） | MVP |
| M3 拆解员 | prompt 模板 → 调无人值守 ZCode → 结构化任务卡；产出不合格自动重试 | MVP |
| M4 执行适配层 | ZCode 适配器（`zcode --prompt --json`，凭证注入、会话跟随）；进度采集（db.sqlite 只读：todo 表=子任务进度、usage 表=成本）；并发上限；worktree 隔离策略 | MVP（ZCode）/ 后期（Codex、Hermes） |
| M5 验收门 | 结果摘要+diff 展示、通过/打回操作；打回=留言回流给原会话（`--resume`） | MVP（简版）/ V0.2（diff 视图） |
| M6 成本观测 | 复用 zcodetoken 的 zusage.py：每任务成本、今日合计、上下文水位 | V0.2 |
| M7 外部抢单 | board MCP 工具 + skill，让任何 ZCode 对话/其它 agent 来板上抢单 | V1.0 |
| M8 多项目板 | 每项目一块板，任务卡绑定工作区路径 | V1.0 |

## 4. 已验证的技术前提（2026-09-06 本机确认）

- **ZCode 原生 headless CLI 存在**：本机 `D:\ZCode\resources\glm\zcode.cjs`（node 执行；CLI 默认不在 PATH，需做一个 shim + 凭证注入，zcode-open-bridge 有现成的 `shared/credentials.py` 方法可搬：json.load 读 `~/.zcode/v2/config.json`，不走 eval）。
- `zcode --prompt "..." --mode plan|build|yolo --json` 单发返回 sessionId/response/usage；`--resume sess_xxx` 恢复；`--target "<objective>"` 长程目标模式。
- **CLI 会话与桌面 App 共库**（`~/.zcode/cli/db/db.sqlite`）→ 看板的进度、成本、代码变更统计可零埋点读出；headless 会话也会出现在 ZCode App 的会话列表里（人可随时 App 内接管）。
- 接单协议语义有现成参考：zcode-agent-board（文件 + `O_CREAT|O_EXCL` 原子锁，claim/done/comment/steal/touch，锁 30 分钟超时可接管）。
- 成本查询直接复用 zcodetoken 的 `zusage.py`（含常驻泵、口径已踩平）。
- **风险项（明示）**：headless CLI 与 ACP 桥均为逆向/实验产物，ZCode 升级可能破坏；与 zcodetoken 同款风险，升级后重验即可。

## 5. 开源项目可用性评估（结论）

**没有 100% 直接可用的**——"发任务 → AI 拆解 → 自主接单 → Web → ZCode 优先"这个组合不存在现成品。差距最小的是 **kanbots**：

| 项目 | 能直接用的部分 | 相对需求的缺口 |
|---|---|---|
| **kanbots** 601★ MIT | autopilot（多角色并行槽≤4、agent 自拆子任务、QA 自检、成本预算熔断）、五列看板、每 run 独立 worktree（防 push 钩子）、决策弹窗、MCP server、SQLite 本地模式 | ❌ 无 ZCode 适配（11 个 CLI + "任意 ACP 兼容 CLI"，ZCode 只能走实验性 ACP 桥或自写适配器）；❌ 英文界面；❌ 与 ZCode 会话体系/成本数据完全隔离（自建 .kanbots/db.sqlite）；⚠️ 2026-05-25 后无提交，趋冷 |
| claude-task-master 28.1k | 任务分解/依赖建模方法论 | 不是看板、不执行任务 |
| zcode-agent-board 1★ | 接单协议语义（文件+锁） | 无 UI、无拆解、无执行器 |
| coder-mcp-bridge | 多后端执行控制面（含 ZCode 后端） | 不是看板，还需上层调度器 |
| vibe-kanban 28.0k | "计划→执行→review"产品范式 | 官宣 sunsetting |

**建议路线**：自研为主，四块积木直接搬（拆解=无人值守 zcode headless；执行=`zcode --prompt`；协议=zcode-agent-board 语义；成本=zusage.py）。kanbots 值得先试装半天，体验其 autopilot 与决策弹窗（交互细节值得抄），但不阻塞自研设计。

## 6. 待确认问题（Q1–Q7，均附推荐）

- **Q1 拆解结果要不要人放行？** 推荐：默认人审放行（防理解跑偏），任务卡可开"自动放行"开关给低风险任务。
- **Q2 执行默认权限模式？** 推荐：改代码类 = `yolo`（无人值守必需）+ 独立 git worktree 隔离 + 验收人审 diff；只读分析类 = `plan`。
- **Q3 并发执行数上限？** 推荐：默认 2，可配置。
- **Q4 任务绑定哪个工作区？** 推荐：任务卡必填工作区路径；git 项目用 worktree 隔离，非 git 项目退化为原目录串行执行。
- **Q5 技术栈？** 推荐：Python（FastAPI + SQLite）后端 + Vite/React 前端——与你现有 Python 工具链（zcodetoken）一致，成本库可直接 import。
- **Q6 headless 会话会出现在 ZCode App 会话列表里（共库），接受吗？** 推荐：接受——反而方便你在 App 内随时接管人工介入。
- **Q7 要不要先试装 kanbots？** 推荐：试装半天体验 autopilot，产出喂需求，不阻塞自研。

## 7. 里程碑

- **V0.1 核心环**：Web 看板 + 发任务 → 拆解员自动拆 → 人放行 → 看板派 ZCode headless 执行 → 进度/成本/结果上板 → 人验收。单并发、单项目。
- **V0.2**：并发队列、打回续做（留言回流）、失败重试与超时接管（steal）、成本面板、自动放行开关。
- **V1.0**：外部抢单（M7）、Codex / Hermes 适配器、多项目多板。
