## 2. 架构：双通道分工

### 2.1 组件清单

**软的一半（让子代理主动说）**

- **S1 协议注入**：主线 a——插件随带 worker 类型定义，协议写进其系统提示词（每请求必重发，上下文压缩清不掉），开关=启用/停用该类型。后备 b——安装器改写用户 `~/.zcode/agents/*.md`（marker 锚点、幂等、可卸载）。兜底 d——派单工具把协议拼进任务描述（依赖模型自觉调用，仅兜底）。
- **S2 协议文本**：三层边界——①后果导向四问（验收标准要变？他人做无效功？不可逆后果？外部阻塞超期？）决定"要不要说"；②锚工件不锚时间 + 两次汇报最少间隔步数 + schema 限长，决定"说多省"；③明示子代理无全局视野，兜底放主代理侧。

**硬的一半（让主代理随时收）**

- **H1 `wait_worker_event(timeout_ms)`**：MCP 工具，阻塞等**任意存活 worker** 的事件，超时返回摘要（沉默检测）。对位 Codex `wait_agent`；ZCode 原生 TaskOutput 只能阻塞单个任务，此为缺位的高价值原语。**单次阻塞时长由插件 mcpServers 配置的 `timeoutMs` 控制**（见 §3-2），无需 55 秒循环近似。**返回值可比 Codex 更好**：Codex 实测只返回 "Wait completed./timed out." 一句话，我们的 H1 监视自己的 spool 文件，可直接返回每个 worker 的待读更新摘要。
  - 设计注意：H1 阻塞期间主代理回合停在工具调用内，用户消息与子代理内核消息都在工具边界排队——`timeout_ms` 保持中等（60–120 秒）让回合定期让出，超时后由模型循环再调（同 Codex awaiter 角色"指数加长等待"策略）。
- **H2 `report(...)`**：子代理侧 MCP 工具，例行汇报写成锚工件文件落到插件自有 spool 目录；H1 监视的就是它。
- **H3 主代理侧兜底（P2 后置）**：心跳质询、转录尾部 peek 核实（勿整读 JSONL）、多 worker 风暴控制。

### 2.2 路由规则（写进 S2 协议文本）

- **紧急 → RespondToCoordinator（内核原生）**：后果四问命中时使用。活跃回合在工具边界送达，空闲直接唤醒主代理新回合（均已本机实证，零开发成本）。
- **例行 → report 落文件（插件）**：里程碑与阶段锚工件使用，受节流规则约束。

### 2.3 不合并到一边的理由

- **纯内核通道不可行**：内核消息对外部进程不可见，H1 无法对它做"任意 worker + 超时"聚合，沉默检测缺失（TaskOutput 只能等单个任务）。
- **纯文件通道不可行**：没有空闲唤醒——主代理结束回合后，文件事件没有任何机制能拉起新回合。

## 3. P0 核验结果（2026-09-08，源码级 + 生产先例，读 zcode.cjs 与 Codex 源码快照）

### 3.1 插件随带 agent 定义——**机制成立，且有生产在用先例**（路径 a 前提证实）

- 内核 `enumeratePluginComponents` 解析 plugin.json 的 `agents` 键：支持对象映射 `{名字: {description}}` 与目录扫描两种形态；插件根下 `agents/` 目录**默认自动发现**（同 skills/），无需显式声明键。
- agent 定义 = frontmatter .md（`name`/`description`/`color`/`tools: [允许工具列表]`，正文即系统提示词），实弹模板见 document-skills 插件 `agents/judge.md`。
- **生产先例**：document-skills 插件缓存目录里有 `agents/judge.md`，本会话 Agent 工具的可用类型里就有 `document-skills:judge`——插件 agent 注册为可派发子代理类型是既成事实，命名空间为 `插件名:类型名`。
- 注册链路核实：内核把内置类型（仅 general-purpose/Explore 两个）与加载的 agent 定义合并进同一注册表，Agent 工具描述动态列出；用户级 `~/.zcode/agents` 与项目级 `<项目>/.zcode/agents` 也走同一注册表（路径 b 的机制面同时得到确认，备用）。
- **残余冒烟（约 1 小时）**：做一个最小插件（agents/worker.md + 一个 echo MCP 工具）实装，确认我们的 worker 类型出现、系统提示词生效、工具限制生效。各项机制均已有生产先例，此步属低风险确认而非探索。

### 3.2 MCP 工具调用超时——**插件可自控，H1 长阻塞可行**

- 内核 `callTool` 超时取值优先级：单次调用 timeoutMs → **MCP 服务器配置 `config.timeoutMs`** → 全局默认；`McpTimeoutError` 超时抛错。
- 服务器配置 `timeoutMs` 由**插件清单 mcpServers 自己声明**（document-skills 配了 90000，生产先例），我们给 wait 工具所在服务器配大值（如 300000–600000）即可单次长阻塞。
- 结论：P0-2 无需冒烟，H1 按"单次长阻塞 + timeout_ms 参数（模型每次调用可调）+ 超时后模型循环再调"设计。

### 3.3 机制面其余复核（全部通过）

当前版本 zcode.cjs（2026-09-07 构建）逐项重验：SendMessage 对运行中子代理 steer 注入（无活跃回合重试 20×10ms 后降级 queued，回执 "sent to its active turn"）；delivery 三态 queued/steered/resumed_background；拒绝三态 no_active_turn/expected_turn_mismatch/turn_not_steerable；RespondToCoordinator（summary≤200/message≤20000，modelInstructions 明文约定收到 "Message from coordinator:" 必回）；`<subagent-message>` 信封格式；会话邮箱（信封 version=1、unread/read 目录、`ZCODE_MESSAGE_ENABLED` 门控、`ZCODE_MAILBOX_ROOT` 覆盖、三个注入点）。
Codex MAV2 对照重验：send_message "Does not trigger a new turn"；followup_task 空闲触发新回合/运行中在消息边界投递；wait_agent V2 = 阻塞等任意存活代理 + 超时摘要 + 用户 steer 可打断（实现：tokio watch 订阅 input_queue 活动，三态 Mailbox/Steered/TimedOut，timeout 由 min/max/default 配置钳制）；awaiter 内置角色（指数加长等待、不许臆断完成、只许终态退出、reasoning effort low）——S2 协议文本可直接借鉴其措辞。

**判定：P0 从"半天两项冒烟"缩为"约 1 小时最小插件实装确认"，架构冻结。**

### 3.4 最小插件实装冒烟——**已通过（2026-09-08 实测）**

以临时插件 `p0-comms`（agents/worker.md + stdio MCP 服务器 ping/slow）本地注册实装，headless 新会话四项验证全部通过：

1. **类型注册**：`p0-comms:worker` 出现在 Agent 工具可用类型清单，与内置及用户级类型并列。
2. **系统提示词生效**：worker 子代理回复以预置探针行 `[p0-worker-protocol-v1]` 开头，并遵守协议规则（先报工具清单）。
3. **tools 白名单生效**：worker 实际仅持有 Read/Bash（frontmatter 声明）+ 内核自动注入的 RespondToCoordinator——**双通道的紧急通道零配置即达**。
4. **timeoutMs 配置被内核采纳**：`ping` 即返正常；`slow(ms=30000)` 恰在 10000ms 报 "Tool execution timed out after 10000ms"。把 timeoutMs 配大即得 H1 单次长阻塞。

附加发现：
- 插件 agent 类型存在**裸名别名**（`p0-comms:worker` 亦可用 `worker` 派发），跨插件有碰撞风险，派发一律用 `插件名:类型名` 全名。
- **headless CLI 独立运行配方**（M4 执行适配层前置，2026-09-08 实测）：`~/.zcode/cli/config.json` 需含 `provider.<id>`（`{kind:"anthropic", options:{apiKey, baseURL}, models:{...}}`，key 从 `~/.zcode/v2/config.json` 的 `builtin:bigmodel-coding-plan` 读——**第一个 enabled 的 builtin:bigmodel 其 apiKey 为空串，勿取**）+ `"model": {"main": "<providerId>/<模型ID>"}`（必须是 provider/model 字符串格式，纯模型 ID 会解析失败）+ 运行时注入环境变量 `ANTHROPIC_API_KEY=<同一 key>`；CLI 的 `--max-turns` 参数在帮助里存在但解析器不认，勿用。
- 冒烟后用户级状态文件（cli/config.json、installed_plugins.json）已从备份还原，插件源码保留于 default 工作区 `tmp/p0-market/` 供 P1 参考。

## 6. 与 Codex MAV2 / 社区对照评估（2026-09-08，应用户要求核查 openai/codex 最新代码与讨论）

**核查基线**：openai/codex 最新 release rust-v0.153.4（2026-09-04）；`multi_agents_spec.rs` 与本地快照逐行一致（872 行，语义未变）；`multi_agents_v2/` 目录文件清单未变；内置角色仍只有 awaiter.toml + 空占位 explorer.toml。

| 设计点 | 我们的方案 | Codex/社区证据 | 结论 |
|---|---|---|---|
| 等待原语 | wait_worker_event 服务器内长轮询，返回带每 worker 事件摘要 | wait_agent 阻塞但**返回仅一句话**（"Wait completed./timed out"）；issue #35259：**19.8% 的 token 花在纯等待/状态轮询的模型回合** | 我们的"返回即信息"设计结构性优于官方；新增 skill 省 token 模式（长批次结束回合等唤醒） |
| 成本控制 | 服务端 2s 硬节流 + summary≤200 + 每批 ≤3 worker 建议 | #14593 "Burning tokens very fast"（630 评论 285 赞）；GA 最佳实践=少而专注、避免过度派生 | 一致，已全部落地 |
| 审计 | 明文锚工件落盘 | #28058（open）：加密消息毁掉可读审计轨迹 | 我们方向正确（明文可审计是刻意选择） |
| 完成唤醒 | RespondToCoordinator 空闲唤醒（已实证） | #15723（open）：后台子代理完成不唤醒调用方；#16900 诉求"状态检查+父子等待"机制 | ZCode 平台原生占优，缺位原语我们已补 |
| 角色注入 | 单一 worker 类型 + 协议烧系统提示词 | Codex 官方角色也只有 awaiter（+空 explorer）；协议放每请求重发通道 | **单类型不是缺陷，与官方形态一致**；扩展路径=用户自定义类型接入（T5 已验证可行） |
| 生命周期 | 会话作用域子代理，结束即终态 | #25179（open）：stale subagents 累积无法可靠关闭 | 我们没有长期 worker 池，无此问题面 |
| 频道隔离 | open_channel 随机后缀 | Codex 无对应概念（mailbox 会话内私有） | 我们跨会话场景的特有解，T8 实测隔离 |
| spawn 前预检 | 未做（以 skill 并发建议缓解） | #23479：spawn 撞线程上限/残留状态，需预检 | 挂账观察：ZCode 侧并发上限未探明，真实使用中留意 |
| 历史 fork/模型指定 | 无（自包含 prompt 补偿） | Codex spawn 有 fork_turns 继承父史、model/reasoning 覆盖 | ZCode Agent 无历史 fork；模型指定可经自定义类型绑定实现，暂不动 |

**总结论**：方案的五个关键抉择（等待返回值带信息、明文审计、服务端节流、单角色+可扩展接入、随机频道隔离）全部经得起最新代码与社区反馈的对照；社区两大结构性痛点（等待空转烧 token、加密毁审计）在我们的设计里分别有结构性规避与刻意反向选择。已采纳两条改进进 skill（每批 ≤3、长批次结束回合模式）。
